# 轻量化状态切换记录软件 PRD

## 1. 项目概述

### 1.1 项目名称
轻量化状态切换记录软件

### 1.2 产品定位
一个本地优先、单用户使用的轻量桌面工具。用户在切换任务、注意力或工作状态时，只需点击一次按钮并选择一个标签，即可记录当前时间点和切换后的状态，并支持导出为 JSON / Excel。

### 1.3 目标
解决“状态切换记录麻烦、事后无法复盘、数据不好整理”的问题。

核心目标：

1. 让用户用最低操作成本记录一次状态切换。
2. 将“时间点 + 状态标签”沉淀为结构化数据。
3. 支持后续复盘、统计、导出和二次分析。

## 2. 使用场景

### 2.1 典型场景

1. 用户从一个任务切换到另一个任务时，点击“记录”按钮。
2. 用户选择当前切换到的状态标签，例如“专注工作”“开会”“休息”“学习”“处理中断”。
3. 系统记录当前时间戳，并保存为一条事件。
4. 用户在日末或周末将记录导出为 Excel，做时间复盘或分析。

### 2.2 目标用户

1. 需要记录专注状态的人。
2. 希望分析任务切换频率的人。
3. 需要保留个人操作轨迹并做数据复盘的人。

## 3. MVP 范围

### 3.1 必做功能

1. 一个主按钮，点击后记录当前时间。
2. 一组状态标签，点击主按钮后必须选择一个标签，表示切换到该状态。
3. 本地存储记录数据。
4. 支持导出 JSON。
5. 支持导出 Excel。
6. 支持查看最近记录列表。

### 3.2 暂不纳入 MVP 的功能

1. 多用户系统。
2. 云端同步。
3. 登录、权限、账号体系。
4. 自动统计图表大屏。
5. 日历视图、复杂筛选器。
6. 手机端同步。

## 4. 核心流程

### 4.1 用户操作流程

1. 打开软件。
2. 首页展示当前状态、主记录按钮、状态标签区、最近记录区。
3. 用户点击“记录当前切换”按钮。
4. 系统弹出或高亮状态标签区。
5. 用户选择一个状态标签。
6. 系统生成一条记录：
   - 记录时间
   - 切换后的状态
   - 上一个状态（如果存在）
   - 记录 ID
7. 系统将数据写入本地存储。
8. 用户可在列表中查看，也可导出为 JSON / Excel。

### 4.2 极简交互原则

1. 单次记录操作不超过 2 步。
2. 默认打开即能点击，不需要进入二级页面。
3. 用户不需要填写复杂表单。
4. 导出动作放在明显位置，但不打断主流程。

## 5. 功能需求

### 5.1 记录按钮

#### 功能描述
提供一个主按钮，用户点击后开始一次状态切换记录。

#### 需求细则

1. 按钮文案建议为“记录当前切换”。
2. 点击时系统应获取本地当前时间，精确到秒，建议保留毫秒。
3. 若未选择标签，则不生成最终记录。
4. 记录成功后提示“已记录：10:25:32 -> 专注工作”。

#### 验收标准

1. 点击按钮后，系统能立即进入标签选择态。
2. 完成标签选择后，生成一条有效记录。
3. 记录时间与用户本机时间一致。

### 5.2 状态标签

#### 功能描述
用户在点击按钮后，从预设标签中选择一个状态，表示“当前切换到什么状态”。

#### 标签示例

1. 专注工作
2. 开会
3. 学习
4. 休息
5. 处理中断
6. 其他

#### 需求细则

1. 标签支持预置。
2. MVP 阶段可先写死在配置中。
3. 被选中标签应有明显高亮态。
4. 选择标签后自动完成保存。
5. 当前状态区域应展示最近一次记录对应的状态。

#### 验收标准

1. 用户能清楚看到可选标签。
2. 点击某个标签后，系统成功保存对应状态。
3. 页面能显示当前激活状态。

### 5.3 记录列表

#### 功能描述
提供最近记录列表，方便用户确认数据是否写入成功。

#### 列表字段

1. 时间
2. 上一状态
3. 当前状态
4. 记录日期

#### 需求细则

1. 默认显示最近 20 条记录。
2. 列表按时间倒序展示。
3. 支持基础删除能力可作为次优先级功能，如果不做删除，至少需要保证导出后可手工处理。

### 5.4 数据存储

#### 功能描述
将每次状态切换保存为结构化数据。

#### 存储要求

1. 本地自动保存。
2. 应用关闭后数据不丢失。
3. JSON 作为主存储格式。
4. Excel 作为导出格式。

#### 验收标准

1. 关闭应用后重新打开，历史数据仍可读取。
2. JSON 文件结构清晰，可直接被脚本读取。
3. Excel 文件可被常见办公软件打开。

### 5.5 JSON 导出

#### 功能描述
支持将记录数据导出为 JSON 文件。

#### 需求细则

1. 支持导出全部记录。
2. 导出文件名建议包含日期，如 `records_2026-04-15.json`。
3. 编码采用 UTF-8。

### 5.6 Excel 导出

#### 功能描述
支持将记录数据导出为 `.xlsx` 文件。

#### Excel 字段建议

1. id
2. recorded_at
3. previous_state
4. current_state
5. state_code
6. date
7. created_at

#### 需求细则

1. 支持一键导出全部记录。
2. 导出文件名建议包含日期，如 `records_2026-04-15.xlsx`。
3. 表头固定，便于后续统计分析。

## 6. 数据结构设计

### 6.1 单条记录结构

```json
{
  "id": "evt_20260415_102532_001",
  "recorded_at": "2026-04-15T10:25:32.481+08:00",
  "date": "2026-04-15",
  "previous_state": "学习",
  "current_state": "专注工作",
  "state_code": "focus_work",
  "source": "manual_click",
  "created_at": "2026-04-15T10:25:32.481+08:00"
}
```

### 6.2 标签配置结构

```json
[
  { "label": "专注工作", "code": "focus_work", "color": "#2563eb" },
  { "label": "开会", "code": "meeting", "color": "#f59e0b" },
  { "label": "学习", "code": "study", "color": "#16a34a" },
  { "label": "休息", "code": "rest", "color": "#8b5cf6" },
  { "label": "处理中断", "code": "interrupt", "color": "#ef4444" }
]
```

### 6.3 本地文件建议

```text
/data
  /records.json
  /states.json
  /exports
    records_2026-04-15.json
    records_2026-04-15.xlsx
```

### 6.4 存储策略建议

建议采用“双层方案”：

1. `records.json` 作为应用主数据源。
2. 导出时按需生成 `.json` 或 `.xlsx` 文件。

这样做的好处：

1. 存储逻辑简单。
2. 数据格式可读性高。
3. 后期切换到 SQLite 成本较低。

## 7. 非功能需求

### 7.1 性能

1. 启动时间小于 2 秒。
2. 单次记录响应时间小于 200ms。
3. 1 万条以内记录读取不卡顿。

### 7.2 易用性

1. 主界面一屏完成核心操作。
2. 重要按钮区域足够大，适合高频点击。
3. 支持键盘快捷键可作为后续增强。

### 7.3 可靠性

1. 写入失败时应有明确错误提示。
2. 导出失败时应提示原因。
3. 数据文件损坏时应具备最基本的容错提示。

### 7.4 可维护性

1. 状态标签配置化。
2. 数据结构明确、便于扩展。
3. 导出模块与记录模块解耦。

## 8. 推荐开发架构

### 8.1 总体架构建议

建议采用“本地桌面应用 + 本地文件存储”的轻量架构，不引入独立后端服务。

原因：

1. 你的核心需求是个人记录，不需要服务端账号体系。
2. 功能简单，前后端分离会带来不必要复杂度。
3. 本地优先更适合低成本开发和长期自用。

### 推荐技术方案 A：Tauri + React + TypeScript

适合想做成正式桌面软件、体积较小、后期可继续扩展的方案。

#### 架构分层

1. 表现层：React
   - 主页面
   - 按钮与标签组件
   - 最近记录列表
2. 应用层：TypeScript Service
   - 创建记录
   - 获取当前状态
   - 读取/写入本地数据
   - 调用导出逻辑
3. 系统层：Tauri
   - 文件系统访问
   - 桌面打包
   - 原生性能支持
4. 数据层：JSON 文件
   - 保存记录
   - 保存标签配置
5. 导出层：Excel 导出模块
   - 将记录转换为 xlsx

#### 优点

1. 比 Electron 更轻。
2. 跨平台能力更好。
3. 本地文件访问方便。
4. UI 开发效率高。

#### 适用结论
如果你希望这个工具后面继续演进，这是最推荐的路线。

### 备选技术方案 B：Python + Tkinter / PySide6

适合非常快地做一个自用版本。

#### 优点

1. 开发速度快。
2. 本地读写 JSON / Excel 非常直接。
3. 更适合个人工具快速验证。

#### 缺点

1. UI 观感通常一般。
2. 打包和跨平台体验不如 Tauri 路线自然。
3. 后期要做更现代化界面时可维护性较弱。

#### 适用结论
如果你的首要目标是“1 到 2 天先做出能用版本”，可以先走 Python。

## 9. 关键设计决策

### 9.1 为什么先用 JSON 而不是直接上数据库

1. 当前数据模型非常简单。
2. 单用户、本地使用，不需要复杂查询。
3. JSON 更方便调试、迁移和备份。
4. 后续如果记录量明显增长，再切换 SQLite 即可。

### 9.2 为什么 Excel 只做导出格式

1. Excel 适合查看和分析，不适合做主写入存储。
2. 直接写 Excel 作为主存储容易出现文件锁定、写入失败和性能问题。
3. 正确方式是 JSON 为主，Excel 为结果产物。

### 9.3 为什么记录“previous_state”

1. 仅记录当前状态时，难以分析切换路径。
2. 有了上一状态，后续可以分析“从什么切到什么”。
3. 便于做切换次数和中断来源统计。

## 10. 开发排期建议

### 第 1 阶段：MVP

预计 2 到 4 天。

1. 搭建基础界面。
2. 实现记录按钮和标签选择。
3. 实现 JSON 持久化。
4. 实现最近记录列表。
5. 实现 JSON / Excel 导出。

### 第 2 阶段：增强版

预计 2 到 3 天。

1. 支持自定义标签。
2. 支持删除或撤销上一条记录。
3. 支持按天筛选。
4. 支持快捷键快速记录。

### 第 3 阶段：分析版

预计 3 到 5 天。

1. 增加每日统计。
2. 增加状态占比图表。
3. 增加切换频率分析。
4. 增加导出统计报表。

## 11. 风险与注意事项

1. 如果标签太多，记录动作会变慢，因此建议 MVP 控制在 5 到 8 个标签。
2. 如果未来要做统计报表，当前字段命名必须规范，避免后续数据难清洗。
3. Excel 导出建议使用标准 `.xlsx` 库，不建议自己拼 CSV 代替。
4. 如果后期考虑多端同步，需提前约束记录 ID 唯一性。

## 12. 验收标准汇总

1. 用户能在主界面 2 步内完成一次记录。
2. 每条记录包含时间和状态信息。
3. 历史记录可查看。
4. 数据重启后不丢失。
5. 能导出 JSON。
6. 能导出 Excel。
7. 导出的文件内容与界面显示一致。

## 13. 最终建议

如果你的目标是：

1. 先快速做出可用版本：选 Python + Tkinter / PySide6。
2. 做成长期可维护的正式轻量桌面应用：选 Tauri + React + TypeScript。

从你当前需求看，我更推荐：

`Tauri + React + TypeScript + 本地 JSON 存储 + Excel 导出`

这是因为它兼顾了：

1. 轻量。
2. 开发效率。
3. 后期扩展。
4. 桌面软件体验。
