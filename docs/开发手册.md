# 开发手册

## 目标

这份手册只管三件事。

第一，后续改动都按同一套流程走。

第二，每次改动都留下可追溯文字记录。

第三，让发布版本和本地源码始终清楚分开。

## 当前项目结构

项目根目录。

- `Sources/StateSwitchMenubar` 是主程序源码
- `Tests/StateSwitchMenubarTests` 是测试
- `docs/PRD_轻量化状态切换记录软件.md` 是产品需求
- `docs/开发手册.md` 是开发流程规范
- `docs/开发日志.md` 是自动生成的开发日志
- `CHANGELOG.md` 是版本级修改日志
- `data/` 是本地数据目录，不进仓库
- `archive/` 是旧方案和实验稿，不参与当前主版本

## 日常开发流程

每次改动都按下面顺序处理。

先明确这次改动属于新功能、修复、重构还是文档更新。

改代码前，先看是否会影响主界面流程、标签数据结构、导出格式，或者浮标交互。

改完后，必须至少跑一次 `swift test`。

如果改动影响使用方式、产品能力、版本行为，就同步更新对应文档。

小改动可以直接在 `main` 上做。稍大的改动建议先开分支，分支名统一用 `feature/...`、`fix/...`、`refactor/...`。

## 提交流程

提交信息统一用下面格式。

`type: 简短说明`

允许的 `type` 只有这些。

- `feat`
- `fix`
- `refactor`
- `docs`
- `style`
- `test`
- `chore`
- `release`

例子。

- `feat: 新增超时提醒设置`
- `fix: 修复设置页按钮点击无响应`
- `refactor: 拆分悬浮浮标状态管理`

## 文档规则

`CHANGELOG.md` 只记版本级变化。准备发版时更新。

`docs/开发日志.md` 记每一次提交。这个文件自动生成，不手改。

`README.md` 只写当前版本怎么运行、怎么使用。

`PRD` 只在产品方向变化时更新。

## 自动日志机制

仓库已经补好一套本地 Git 工作流。

执行一次下面命令就会安装。

`scripts/install_git_workflow.sh`

安装后会生效三件事。

第一，提交信息会校验格式，不符合规则不能提交。

第二，每次提交后会自动刷新 `docs/开发日志.md`，并把日志写回当前这次提交里。

第三，推送前会自动跑 `swift test`，测试不过不能推。

## 发版流程

发版前检查四件事。

先跑测试。

再更新 `CHANGELOG.md`。

再确认 `README.md` 和实际功能一致。

最后再打包到发布目录，版本号保持一致。

## 注意事项

`data/` 里是个人使用数据，不提交。

`docs/开发日志.md` 是生成文件，不要手改，不然下次提交会被重写。

如果只是临时实验，放到 `archive/`，不要混进主程序。
